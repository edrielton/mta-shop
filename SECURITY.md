# Segurança e Boas Práticas - MTA Shop\n\n## 🔐 Princípios de Segurança\n\nEste documento descreve as práticas de segurança implementadas no projeto MTA Shop.\n\n### 1. Variáveis de Ambiente\n\n**✅ FAÇA:**\n- Use `.env.example` como template\n- Nunca commita `.env` com valores reais\n- Configure variáveis no painel do seu provedor (Vercel, Netlify, etc)\n- Use valores diferentes para dev, staging e produção\n\n**❌ NÃO FAÇA:**\n- Committar chaves API no código\n- Compartilhar `.env` com valores secretos\n- Usar mesmas chaves em múltiplos ambientes\n- Commitar senhas ou tokens\n\n### 2. Chaves de API\n\nTodas as chaves públicas estão safe para usar no frontend:\n- `VITE_STRIPE_PUBLIC_KEY` (pk_test_* ou pk_live_*)\n- `VITE_MERCADOPAGO_PUBLIC_KEY`\n- `VITE_GOOGLE_ANALYTICS_ID`\n\n**Nunca exponha:**\n- Chaves secretas (sk_* do Stripe)\n- Tokens de API privados\n- Senhas de banco de dados\n- Chaves JWT privadas\n\n### 3. Autenticação & Autorização\n\n- Sempre use HTTPS em produção\n- Implemente autenticação via OAuth quando possível\n- Use JWT com expiração curta (15-30 min)\n- Refresh tokens com expiração longa (7-30 dias)\n- Nunca armazene senhas, sempre faça hash (bcrypt)\n\n### 4. Dados Sensíveis\n\n**Remova antes de committar:**\n- Email ou dados de contas\n- URLs de produção\n- IPs internos ou domínios privados\n- Nomes de usuários administrador\n- Tokens de teste ou produção\n\n### 5. Dependências\n\nMantenha regularmente:\n```bash\n# Verificar vulnerabilidades\nnpm audit\n\n# Atualizar dependências seguras\nnpm update\n\n# Verificar dependências desatualizadas\nnpm outdated\n```\n\n### 6. GitHub Security\n\n**Ative no seu repositório:**\n1. Settings → Code security and analysis\n   - ✅ Dependabot alerts\n   - ✅ Dependabot security updates\n   - ✅ Secret scanning\n\n2. Settings → Secrets and variables\n   - Adicione seus valores secretos como secrets\n   - Use `${{ secrets.NOME_DO_SECRET }}` nos workflows\n\n### 7. Branches e Colaboração\n\n**main**: Código em produção (protegido)\n**feat/static-site**: Desenvolvimento (rebase seguro)\n**backup/full-stack-original**: Backup do código original\n\nRegras de proteção:\n- Requerer PR review antes de merge\n- Bloquear pushes diretos\n- Requer status checks passing\n\n### 8. Commits e Histórico\n\n- Use mensagens de commit descritivas\n- Evite committar secrets acidentalmente\n- Se cometeu erro, use `git-secrets` para prevenir\n\n**Instalar git-secrets:**\n```bash\nbrew install git-secrets  # macOS\nchoco install git-secrets # Windows\nsudo apt-get install git-secrets # Linux\n\n# Configurar\ngit secrets --install\ngit secrets --register-aws\n```\n\n## 🚨 Se Você Commitou um Secret\n\n1. **NUNCA** deixe no histórico\n2. Use `git filter-branch` ou `BFG Repo-Cleaner`\n3. Regenere a chave imediatamente\n4. Force push (avise a equipe)\n\n```bash\n# Remover arquivo do histórico\ngit filter-branch --tree-filter 'rm -f .env' HEAD\ngit push origin --force --all\n```\n\n## 📋 Checklist de Segurança\n\nAntes de fazer push:\n\n- [ ] Nenhum `.env` com valores reais\n- [ ] Nenhuma chave API privada\n- [ ] Nenhuma senha ou token\n- [ ] Nenhum email ou dados pessoais\n- [ ] Nenhuma URL de produção\n- [ ] `.env.example` atualizado com template\n- [ ] `.gitignore` contém `*.env`\n- [ ] Dependências sem vulnerabilidades (`npm audit`)\n- [ ] Não há `console.log()` com dados sensíveis\n- [ ] Não há comentários com credenciais\n\n## 🔗 Referências\n\n- [OWASP Top 10](https://owasp.org/www-project-top-ten/)\n- [GitHub Secret Scanning](https://docs.github.com/en/code-security/secret-scanning)\n- [npm Security Best Practices](https://docs.npmjs.com/packages-and-modules/security)\n- [Stripe Security](https://stripe.com/docs/security)\n- [Mercado Pago Security](https://www.mercadopago.com/developers)\n\n---\n\n**Lembre-se:** A segurança é responsabilidade de todos! 🛡️\n"
